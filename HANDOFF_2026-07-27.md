# WSDA Video Engine — Full Handoff (2026-07-27 session)
# For: continuing development with a different AI assistant (Kimi)
# Repo: github.com/walterashields/wsda-video-engine

## What this system is

An automated pipeline that turns a topic into a finished instructional video:
`research.py` (topic → content brief) → `draft.py` (brief → narrated production
card + verified SQL/database) → `produce.py` (card → recorded, narrated,
QA'd MP4). A Flask web UI (`studio.py`) wraps the whole pipeline behind a form.

This document covers one very long, dense session of bug-hunting and feature
work. Read this before touching the code — nearly every fix below exists
because a *specific, reproduced* bug was found, not because of speculation.
The commit history (`git log`) has ~37 commits from this session, each with
a real rationale in the message.

---

## Architecture, in one paragraph

`research.py` calls Claude to produce a `brief.json` (topic, hook, scenes,
format). `draft.py` reads that brief and, for SQL lessons, does something
important: it builds a **real SQLite database and executes the real teaching
queries FIRST**, captures the actual verified results, and only THEN asks
Claude to write narration — grounded in those real numbers, not invented
ones. This "verify first, narrate second" inversion is the single most
important architectural decision in the whole system (see "The original bug"
below). `produce.py` then orchestrates: number pre-check → visual recording
(Playwright driving a custom web SQL-viewer or chat-demo app) → ElevenLabs
narration synthesis → timing QA → trim → final MP4.

Only two adapters actually exist and work: `adapters/sql_viewer_adapter.py`
and `adapters/chat_demo_adapter.py`. Excel/Power BI/Python are UI-disabled
placeholders — no code exists for them. Don't let anything re-enable them
without building real adapters first.

## The original bug (why most of `draft.py` looks the way it does)

Before this session, `draft.py` wrote narration FIRST (blind, no idea what
data existed), then generated SQL separately (blind to the narration), and if
that SQL didn't happen to define real tables, silently fabricated placeholder
data ("Sample A/B/C"). Narration and visuals were never connected to a shared
source of truth. Fixed by flipping the order: `build_verified_sql_and_db()`
now builds the DB and runs every query for real before any narration gets
written, and the verified results get fed into the narration prompt as
`VERIFIED DATA` — the only facts narration is allowed to use.

Everything else in this session is downstream of that fix, in one of two
ways: (a) closing gaps in the grounding/verification system itself, or
(b) fixing things that were only ever exposed once real, number-dense,
narrated video was actually being produced.

## Chronological map of what got fixed and why (read this before changing anything)

### 1. Core grounding pipeline (draft.py)
- `build_verified_sql_and_db()` — generates a self-contained SQL file
  (schema + seed data + teaching queries), builds a real DB, runs every
  query, retries up to 3x on failure. **Enforces a query-section cap**
  (default 4, scaled to 1 for `micro` format) because early tests showed
  the model happily building 12-section "lessons" covering 5 unrelated root
  causes when the topic naturally had multiple possible explanations —
  massively over-scoping a "short" lesson. A hard-coded structural check
  (`len(sections) > max_sections`) rejects and retries; a prompt rule alone
  wasn't reliable enough.
- `check_number_mismatches()` — verifies every number in narration against
  the REAL query results. Went through several real-bug iterations:
  - v1: pooled all query results into one flat set — missed a number that
    was real for query A but wrongly cited under query B's narration.
  - v2: fixed to correlate per-event via `query_ref`, matching how the
    *actual* production gate (`narration/check_numbers.py`) already worked
    — but this was TOO strict: it rejected legitimate "compare this new
    result to the wrong total we saw earlier" narration (a real, valid
    teaching pattern), causing the model to loop 3x on a genuinely correct
    sentence.
  - v3 (current): a number is valid if it matches the CURRENT event's query,
    OR any query already revealed earlier in the timeline — cumulative
    reveal, not just current-query-only. This is the version to keep.
- `check_where_date_literals_mentioned()` — real bug: narration said "the
  cutoff" repeatedly but never stated what the actual cutoff DATE was, so a
  viewer couldn't verify the classification logic. Known limitation: this
  check only compares YEAR, so it can be fooled by an unrelated date
  mention sharing the same year (confirmed false-negative in testing). The
  strengthened `REVIEW_SYSTEM` prompt (holistic reviewer, see below) is the
  more precise fix for this nuance; the deterministic check is a coarse
  backstop only.
- `check_sql_matches_topic()` — if the lesson title/hook centers on a
  specific SQL construct (WHERE, JOIN, GROUP BY, etc.), the real SQL must
  actually contain it. Real bug caught: a "WHERE clause" lesson whose query
  only had a GROUP BY.
- `check_unbuilt_concept_claims()` — narration asserted "filters are
  matched" with zero query anywhere demonstrating filters (scope-capping
  had dropped that cause but the narration's framing didn't update to
  match). Note: a naive "N steps promised vs N real sections" count
  wouldn't have caught this — there were MORE real sections than promised
  steps, just covering fewer distinct concepts. Check is keyword/concept
  based, not count based.
- Number extraction (`extract_spelled_number_mentions`) had two real bugs,
  both fixed:
  - Bare magnitude words ("a hundred percent") were parsed as literal 100 —
    fixed to require a real preceding number before a magnitude word
    counts.
  - Adjacent numbers across punctuation got merged ("order 1001, eighty-four
    forty-nine" → parsed as one garbage number 1085.49) because punctuation
    was stripped before scanning. Fixed by splitting on punctuation FIRST.
- Number tolerance is scaled by magnitude: exact to the cent below $100,
  whole-dollar rounding allowed at $100+ (a real stuck-retry-loop was caused
  by requiring "eleven thousand eight hundred forty-eight dollars and
  seventy-five cents" — nobody speaks four-figure amounts that precisely).

### 2. The Teaching Quality Gate (draft.py) — most recent, most important addition
Everything above verifies CORRECTNESS (is this true). Nothing verified actual
teaching QUALITY (is this good) until `review_teaching_quality()` was added.
It scores 5 dimensions (clarity, hook, why-it-matters, analogy quality,
emotional register) against a strict rubric, gives 2 chances to fix specific
feedback, and — this is the important part — **hard-fails the lesson with
`RuntimeError` if it still doesn't clear the bar.** This is deliberately
different from the correctness retry loop, which still ships a "best effort"
after 3 failed attempts. For quality specifically, the owner (Walter)
explicitly wants nothing shipped below the bar. Do not weaken this to "ship
anyway" without explicit instruction — that would silently undo the entire
point of the feature.

### 3. Holistic fidelity reviewer (draft.py: `review_lesson_fidelity`)
A separate LLM call (not a keyword check) that reads the finished lesson as
a skeptical viewer and checks whether SQL/narration actually deliver on the
title/hook's promise. Catches things keyword checks structurally can't (e.g.
distinguishing "the actual threshold value" from "a coincidentally similar
value elsewhere in the data" — confirmed the deterministic date check gets
fooled by exactly this).

### 4. Recording/adapter fixes (adapters/sql_viewer_adapter.py, web/templates/viewer.html)
- Schema-panel cursor scan was hardcoded to 3 waypoints from the ORIGINAL
  hand-built 3-table NovaBridge lesson — visited a phantom 3rd position
  regardless of actual table count. Fixed to scan dynamically based on real
  schema.
- Schema columns were never actually expanded/visible on screen —
  `_scan_schema()` moved the cursor near tables but never called
  `activateTable()` to reveal columns. Narration described column names
  that were literally never shown.
- `highlightSection()` used `scrollIntoView({block:'start'})`, which cuts
  off the bottom of any query taller than the viewport. Fixed to center
  when it fits.
- `_collapse_sql_pane()`/`_expand_sql_pane()` triggered a 0.4s CSS
  transition and returned immediately with zero wait — narration got
  scheduled to start before the pane had actually finished animating into
  view. This was the root cause of "narration starts talking about the
  result before it's displayed."
- "Frozen screen" bug: a card had 3 narrated "traps" but only built visual
  content for 1 — traps 2/3 just re-highlighted the same already-shown
  section with new narration on top, producing zero visual change for the
  rest of the video. Fixed with both a prompt rule and a structural
  `validate_card()` check that rejects consecutive `highlight_section`
  events with the same target and nothing in between.

### 5. Timing (draft.py, narration/qa.py, narration/audit_narrator.py, produce.py)
- Pause durations were sized by naive word count, which drastically
  undercounts numeric-heavy narration ("23950.00" is one word by count but
  takes 2+ seconds to say). Fixed with `_spoken_word_units()`, a
  numeric-aware weighting.
- The pre-existing duration-cap logic uniformly scaled EVERY pause by the
  same ratio to hit a format's time limit — squeezing number-dense blocks
  exactly as hard as simple ones. Replaced with `enforce_duration_cap()`,
  which compresses only slack above a real per-event floor, and reports
  honestly if a script genuinely needs more time than the format allows
  rather than corrupting timing to force it.
- `narration/qa.py`'s pause-duration auto-fix used a hardcoded string
  pattern expecting quoted YAML values — broke silently (reported "Fixed 0
  pause durations") once `draft.py` started emitting unquoted plain
  scalars. Fixed to edit the parsed YAML structure directly instead of
  string-matching raw text — this is a general lesson: **never rely on
  string-matching output text or file existence to determine success;
  check exit codes and parsed data.**
- `narration/audit_narrator.py` swallowed per-clip synthesis exceptions and
  proceeded to "successfully" render a completely silent video, reporting
  "Production complete" — this actually happened (ElevenLabs 401s, all 11
  clips failed, video still "succeeded"). Fixed with a hard gate: ≥50%
  clip failure now halts production loudly instead of shipping a mute
  "success." `produce.py` was ALSO ignoring the actual exit code from this
  step, inferring success from string-matching output — fixed to check
  exit code explicitly.

### 6. Content-accuracy / tool-mismatch (draft.py: `detect_adapter`)
`detect_adapter()` had zero handling for excel/powerbi/python — anything
selected besides SQL silently fell through to the chat_demo adapter
regardless of the actual tool, meaning a lesson could narrate "open Excel"
while the screen showed a chat interface. Fixed to raise a clear error if a
lesson's own scenes call for an unbuilt adapter, rather than silently
substituting the wrong visual. UI (studio.py) now marks Excel/Python/Power
BI as disabled "(coming soon)" instead of offering something the pipeline
can't deliver.

### 7. Pronunciation (draft.py: DRAFT_SYSTEM prompt)
Went through several real, evidence-based iterations:
- Raw digit strings with commas ("23,950.00") get mangled by the voice
  engine — fixed by requiring numbers be spelled out in words.
- snake_case identifiers read as literal underscored garbage — fixed to
  require natural-language expansion ("customer_id" → "customer ID").
- Bare abbreviations with no separator ("id", "qty", "amt") still get
  mispronounced even after snake_case fix — added explicit handling: add
  table-name context ("id" in a customers table → "customer ID").
- Meta-lessons ABOUT cryptic naming (deliberately showing "cust_eml" as the
  teaching point) need special handling — say it as fragments AND state
  the plain-English meaning in the same breath, don't just read the raw
  string as a fluent word.

### 8. Content quality / clarity prompting (draft.py: DRAFT_SYSTEM)
Abstract "be clear and funny" instructions consistently underperformed
concrete guidance. What actually moved quality:
- A required CLARITY TECHNIQUE: translate any technical term into a
  physical/everyday image in the SAME sentence, not as a follow-up.
- A full worked example embedded directly in the prompt (few-shot beats
  abstract rules).
- Concrete humor mechanisms (character, timing, understatement) instead of
  "be funny."
- STATE THE ACTUAL THRESHOLD rule (see check_where_date_literals_mentioned
  above) — a WHERE-clause boundary value must be spoken explicitly, not
  referenced abstractly as "the cutoff."

### 9. Scope: Micro format (research.py, draft.py, studio.py)
New 1-3 minute format tier, fully wired: `research.py` caps scenes to 1-2
and targets ~2 min; `draft.py` caps SQL sections to 1 and adds explicit
brevity/hook/no-checklist guidance; `studio.py` has a "Micro" format chip.

### 10. Hands-on style / exercise files (draft.py, research.py, studio.py)
Real bug: `handson` (heavy/moderate/light) was read from the web form but
NEVER passed to research.py at all — completely dead field, produced zero
difference in output regardless of selection. Same was true of `level`,
`length`, and `notes`. Fixed to actually flow through as enriched-topic
guidance text. Additionally, "heavy/moderate" hands-on now generates REAL
exercise files (`generate_exercise_files()`): a CSV export of the lesson's
actual verified data, a starter SQL file with teaching queries blanked out
(schema/seed data intact), and an answer key. Before this, "heavy hands-on"
produced literally nothing regardless of selection — pure UI theater.
Also fixed: hands-on-style chips were incorrectly configured as multi-select
(could pick heavy+moderate+light simultaneously) — now single-select like
every other exclusive-choice field.

### 11. Topic Scouting (topic_scout.py — new file)
On-demand, web-grounded topic research since no real sales/analytics data
exists. Fixed category taxonomy (4 categories, confirmed with the project
owner — do not add/remove without checking). Scans local `research/` and
`courses/` history to avoid suggesting duplicates. Uses Claude's server-side
`web_search` tool and requires every suggestion to cite a real URL.
**Real bug already found and fixed**: when web search actually runs,
`response.content` contains MULTIPLE text blocks (the model's "I'll search
for..." commentary, then the final answer) — joining them all together
prepends commentary in front of the JSON and breaks the parse. Fixed to
take only the LAST text block. If you see "no suggestions produced" again,
check this first.

### 12. Infrastructure/environment gotchas
- `studio.py` originally ran on port 7000, which conflicts with macOS
  AirPlay Receiver (returns a misleading "Access Denied / 403" HTML page,
  not a normal connection-refused error). Moved to port 7010.
- ElevenLabs credentials: `studio.py`'s call to `produce.py` wasn't passing
  `--el-key`/`--el-voice` explicitly, silently falling back to a different
  system voice when env vars weren't set in the Flask process's
  environment. Fixed to read `ELEVENLABS_API_KEY`/`ELEVENLABS_VOICE_ID`
  explicitly and warn loudly if missing.
- `studio.py` originally only drafted/produced the FIRST lesson of any
  multi-lesson brief. Fixed to loop over every lesson, tracking per-lesson
  success/failure so one bad lesson doesn't kill the whole batch.

## Known limitations — do not "fix" these without a real design conversation

1. **Multi-tool switching is explicitly out of scope for now.** A lesson
   needing both a chat interface AND a SQL viewer (e.g. "paste your schema
   into ChatGPT") currently can only use ONE adapter for its whole
   duration. The owner and previous assistant explicitly agreed to park
   this as its own dedicated session — it requires real engine changes
   (`engine/timeline_runner.py` currently opens one browser page and picks
   one adapter for an entire lesson; supporting a switch requires either
   segment-and-concatenate recording or a genuinely new runtime).
2. **Excel/Power BI/Python have no adapters.** Don't re-enable their UI
   chips without building real Playwright-driven mock UIs for them first —
   this is comparable in scope to the SQL adapter itself, including a
   parallel "verified data" pipeline.
3. **The `check_where_date_literals_mentioned` year-only check has a known
   false-negative** (confirmed via testing) when an unrelated date shares
   the cutoff's year. The holistic reviewer's strengthened prompt is the
   intended real fix for this nuance; don't over-invest in the
   deterministic version.
4. **Tool selection UX is still manual chips**, though a design discussion
   concluded the better long-term answer is the system auto-detecting the
   right tool from topic content and displaying its choice, rather than
   asking the user to pick from options that don't reliably drive anything
   downstream (`detect_adapter()` already ignores the UI selection and
   infers from lesson content). This was discussed and agreed as directionally
   correct but NOT YET IMPLEMENTED — confirm with the owner before building.
5. **Teaching Quality Gate cost**: adds up to 2 extra API calls per lesson.
   Owner is aware and accepted this tradeoff explicitly.

## How to actually test changes

The reliable workflow all session: make a code change, have the owner run
the CLI/web UI locally (draft.py/produce.py or studio.py), get the real
console output back, diagnose from real evidence — never guess blind. Files
land in `research/<slug>/brief.json` and `courses/<slug>/video_1_N/` —
pushing these to git lets a remote assistant inspect the actual generated
content (SQL, database, production card YAML) directly rather than working
from descriptions.

Quick sanity checks before trusting any change:
```bash
python3 -c "import ast; ast.parse(open('draft.py').read())"  # syntax
python3 studio.py   # web UI at :7010
python3 draft.py research/<slug>/brief.json --lesson 1
python3 produce.py courses/<slug>/video_1_1/production_card.yml
```
